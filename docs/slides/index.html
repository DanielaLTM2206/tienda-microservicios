El Problema y Dominio del MVP

Contexto de Diseño

El Problema

  • Monolitos Acoplados: Los sistemas tradicionales sufren bloqueos síncronos en cascada, degradando disponibilidad y escalabilidad global.
  • Protocolo Único: Tratar toda la comunicación interna como HTTP REST es ineficiente; no garantiza entrega en flujos asíncronos.
  • Pérdida de Identidad de Errores: Al cruzar fronteras de red, los errores se vuelven genéricos e impiden diagnósticos rápidos.

Dominio Simplificado

  • Pedidos (svc-pedidos): Microservicio central que gestiona el ciclo de vida del pedido, escribe en su BD local y propaga eventos.
  • Productos (svc-productos): Catálogo maestro que valida disponibilidad ante solicitudes síncronas.
  • Notificaciones (svc-notificaciones): Consumidor desacoplado que reacciona a eventos de broker.
  • API Gateway: Punto único HTTP que traduce REST → TCP/gRPC y aplica seguridad.

Avance 2: gRPC + RabbitMQ

Contratos y Garantías de Entrega

El contrato único vive en libs/proto/ (raíz del monorepo) y es copiado a cada imagen Docker en build. Una sola fuente de verdad evita la divergencia de esquemas entre servicios.

  • Tipado Estricto: Validación en tiempo de compilación con Protocol Buffers.
  • Eficiencia: Serialización binaria sobre HTTP/2, más compacta que JSON.
  • Error Controlado: Producto inexistente retorna encontrado=false sin caer el servicio.
// libs/proto/productos.proto
syntax = "proto3";
package productos;

service ProductosService {
  rpc ObtenerProducto (ProductoRequest)
      returns (ProductoResponse);
}

message ProductoResponse {
  int32  id         = 1;
  string nombre     = 2;
  double precio     = 3;
  bool   encontrado = 5;
}

Garantía de entrega crítica para el stock

  • Cola Durable stock_actualizar: Los mensajes persisten en disco en el broker y sobreviven reinicios del servicio.
  • Si svc-notificaciones cae, RabbitMQ retiene el mensaje indefinidamente hasta que el consumidor se recupere y envíe un ACK.
  • Redis (Avance 1) es volátil: mensaje publicado sin consumidor activo = mensaje perdido para siempre.
// svc-notificaciones — RabbitMQ consumer
@EventPattern('stock.actualizar')
async handleStockActualizar(
    @Payload() data: StockPayload) {
  this.logger.log(
    `🐇 [RabbitMQ] Evento recibido`
  );
  await this.service.procesarStock(data);
}

Avance 3: Seguridad y Observabilidad

JWT, Guards y Sentry

Autenticación y Autorización JWTGuard

  • Política "Denegar por Defecto": El JwtAuthGuard global protege absolutamente todas las rutas. Solo las decoradas con @Public() son accesibles sin token.
  • RBAC con RolesGuard: El RolesGuard valida el rol incluido en el payload del JWT. Un cliente intentando crear un pedido (rol admin) recibe 403 Forbidden.
  • Stateless: Sin sesiones en BD. La validez se confirma matemáticamente en cada request con JWT_SECRET. El token expira en 1 hora.

Monitoreo Activo Sentry

  • Filtrado Inteligente: Solo se reportan errores 5xx (servidor). Los 4xx (cliente) son ignorados conscientemente para no generar ruido en el panel de alertas.
  • Contexto Enriquecido: Cada captura incluye el servicio de origen (service=gateway), el transporte utilizado (transport=HTTP), la URL, el método y el payload de la petición.
  • Sin dependencia dura: Si SENTRY_DSN no está definido, los servicios arrancan normalmente sin error ni advertencia.

Conclusiones y Lecciones Aprendidas

Cierre Metodológico

Aprendizajes Técnicos

  • No existe un transporte universal: gRPC provee contratos fuertes para validaciones síncronas críticas; RabbitMQ garantiza la integridad del stock con colas durables; Redis ofrece velocidad para alertas no críticas.
  • El Gateway como capa de seguridad central: Autenticar y autorizar en el Gateway descarga a todos los microservicios internos de procesamiento de tokens.
  • Observabilidad inteligente: Monitorear no es guardar todo — filtrar 4xx de Sentry elimina el ruido y enfoca las alertas en fallas reales de infraestructura.

Mejora del Proceso

  • Deuda Git reconocida: En los Avances 1 y 2, el código se subió en commits gigantescos a main. Se documenta con honestidad para el jurado.
  • Corrección (Avance 3): Implementación real de GitHub Flow: ramas de trabajo, Pull Requests con revisión cruzada, commits incrementales con identidad de los tres integrantes.
  • Kanban vinculado: Tarjetas ligadas a Issues y PRs del repositorio, tablero público para auditoría.

Preguntas del Jurado

Defensa de Arquitectura: Q&A

Preguntas Probables y Respuestas Preparadas
¿Qué información viaja dentro de un JWT y cómo se valida en el servidor?
El token JWT tiene tres partes en Base64 URL: Header.Payload.Signature. El payload contiene sub (ID), username y rol. El JwtStrategy recalcula la firma con JWT_SECRET en cada petición — si coincide y el token no expiró, inyecta el payload en request.user. Stateless: sin sesión en base de datos.
¿Cuál es la diferencia entre un Guard de NestJS y un Middleware?
Un middleware corre antes del enrutamiento, sin visibilidad del handler de destino ni de sus decoradores. Un Guard corre después del routing pero antes del handler, con acceso al ExecutionContext, lo que le permite leer metadatos como @Public() o @Roles('admin') para aplicar políticas de acceso finas (401/403).
¿Por qué gRPC en el salto pedidos → productos y no TCP simple o eventos?
1) Contract-First: el archivo .proto compartido garantiza tipado estricto y detecta cambios de esquema en compilación, no en ejecución. 2) La creación del pedido requiere confirmar la disponibilidad del producto antes de persistir — un evento asíncrono no sirve porque no hay respuesta de confirmación.
¿Por qué RabbitMQ para el stock y Redis para las notificaciones?
Redis Pub/Sub es volátil: si el consumidor está apagado cuando se publica, el mensaje se pierde. La actualización de stock es crítica — no se puede perder datos. RabbitMQ usa colas durables: persiste el mensaje en disco hasta recibir el ACK del consumidor, garantizando la consistencia eventual incluso ante caídas temporales del servicio.
